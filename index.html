Conclusions (for clean re-runs)

  • Speed stays constant throughout a clean run and there's no gradual slowdown or a slow warm-up. The amount of computation done per step stays nearly constant. Some changes in speed are due to the increase/decrease in network waiting times.
  • Because of this, a smaller 5000 step simulation would have worked just as well. Not only would it have eliminated the need to run multiple simulations together at the same time, it would have also decreased the chance that someone else's run would slowdown ours.
  • Speed changes observed were because of other jobs sharing the network and some of them were out of our control since the lab machines are open access and other users had their processes running as well.
  • Noise in speed (time per step) varied more for runs using more nodes (machines). Time per step varied less than 3% on 4 nodes, 5% on 8 nodes, and 7% on 16 nodes.

Pointers

  • Final MLUPS are noisy. The network is shared with the rest of the lab so similar runs can spend different times waiting (see Scaling).
  • A marker is placed where the median speed over the next 2000 steps differs from the previous 2000 by at least 12% along with the most likely cause for the change in speed.
  • The “clock time” x-axis option lines up runs against each other which makes lab events (reboots, network outages, etc.) easier to point out.
  • Faded lines are attempts that were stopped (due to reboots, memory limit exceeds, network failures and other users' processes appearing on our machines for the clean runs). They're excluded from all result calculations.

How we got this data

Each run writes a progress line to its log every 200 steps. The controller checks the active runs and the machines they run on for any other process started by another user every 60s. This is what is used to figure out the most likely cause for slowdowns and speedups.

CPU scaling analysis

Case A: Monitoring on / off AVX2 + SSE3 · 8 workers/node

Monitoring slows the computing part, but on 8 and 16 nodes most of each step is waiting for the network, so the total changes little and network noise can outweigh it.

Case B: SIMD analysis Monitoring on · 8 workers/node

No build “wins” consistently. Differences in the total come mainly from time spent waiting for the network, not from computing. For each line, the 4-node run is considered the baseline i.e. 8-node run with no intrinsics is 1.97 times faster than 4-node run with no intrinsics for example.

Case C: Workers per node AVX2 + SSE3 · Monitoring on

4, 8 or 12 worker processes per machine. For each line, the 4-node run is considered the baseline i.e. 8-node run with 12 workers is 1.14 times faster than 4-node run with 12 workers for example.

Conclusions

From the clean runs on the i7 machines (choose “clean re-runs only” to see just these).

  • More nodes made computing faster but not waiting. In Cases A and B the slowest worker's computing time fell 2.7–5.2 times from 4 to 16 nodes (4 times the machines would ideally give 4 times). Waiting time didn't fall and in 3/4 it grew so by 16 nodes, waiting took 3–7 times as long as computing. 8 nodes was hence the sweet spot. 16 nodes was slower than 8 in 3/4. The two settings not plotted here (SSE3 only and no intrinsics, both with monitoring off; see All results) behaved the same way.
  • Case A, monitoring: monitoring made the slowest worker's computing 12–22% slower. With monitoring on the whole simulation took 10% longer than with it off at 4 nodes while taking about the same time for 8 node off/on. At 16 nodes the monitoring-off run was the slower one, because it waited much longer due to the network being slower.
  • Case B, builds: no build computes consistently faster. The build that “wins” changes between different node counts: no intrinsics at 4 nodes, AVX2 at 8, SSE3 at 16. Lattice Boltzmann computation is usually limited by memory speed (bandwidth) than arithmetic which could explain why wider vector instructions don't help. The larger differences in MLUPS such as SSE3 and no intrinsics at 208–212 MLUPS vs AVX2 at 170 on 8 nodes come from waiting. Here AVX2 waited about 1.7 times as long compared to the other two.
  • Case C, workers per node: at 4 nodes, 4 and 8 workers per node tied (122.5 MLUPS each). At 8 nodes, 4 workers (208) beat 8 (169): its computing was slower but it waited about half as long. 12 workers per node was the slowest at every node count. Each of its workers had 1/3 less to compute compared to 8 but its slowest worker took longer compared to 8 workers at every node count. The 4 extra processes run on the slower E-cores (reference) and everyone waits for the slowest. At 16 nodes, 4 and 8 workers were about equal (186 and 189 MLUPS).

Pointers

  • One setting corresponds to one run. Clean re-runs keep other users' programs off our machines, but the lab network is still shared so waiting time still varies a lot between similar runs. Small differences between lines aren't that meaningful.
  • Computing and waiting don't add up exactly to the total (they make up 86–99% of it). The slowest worker isn't always the one that waited least. Some time also goes to monitoring and other bookkeeping.
  • Speedup is relative to each line's own 4-node run. If the 4-node run ran on a slower network, this can cause other runs to seem better than they are.

How we got this data

Simulation time is the total from each run's report.txt (written by HemePure at the end of the run). Start-up (reading the .gmy file) isn't included. The lower plots in each case use “LB calc only” (computing) and “MPI Wait” (waiting for messages from other workers) from report.txt which HemePure records for every worker. Computing plot shows the slowest worker since every step waits for it. Waiting shows the worker that waited least time i.e. waiting time no worker could avoid.

TASK 3 · MPI PROFILING

Blood flow over one heartbeat

At the two moments of strongest flow t = 0.20 s into the aneurysm · t = 0.62 s back out

Conclusions

  • The simulation shows that blood moves in and out of the aneurysm with each heartbeat. It flows in most strongly at 0.20 s and back out most strongly at 0.62 s. This comes from how the case is set up and not from real blood flow (see below).
  • Blood in the main vessel moves at over 1 cm/s but inside the aneurysm it is much slower. The deepest cross-section (plane 3) has 4–5 times weaker flow than the one nearest the vessel (plane 1).

How realistic is this?

The vessel's shape is realistic but the flow is not. The case is built to stress test the computation.

  • Realistic: the geometry is a basilar artery (deduced from the BA in the .gmy file name), slow flow inside compared with the main vessel which is also seen in real aneurysms.
  • Not realistic: flow pressure is pretty small so blood goes back and forth at roughly 30–50 times lower speed than in a real artery. Real brain arteries carry blood forward through the whole heartbeat. At real speeds blood enters an aneurysm and swirls around inside it.
  • None of this affects the speed results in Task 1 as each step does the same amount of computing either way.

Pointers

  • Speed pictures use one colour scale (dark = still, yellow = fast). The cross-sections show flow through the plane and red = deeper into the aneurysm, blue = back out, grey = still. Each cross-section has its own scale because plane 3's flow would be almost invisible on plane 1's scale.
  • The arrows show direction only.
  • HemePure only saves the cut planes listed in the input file and the full volume is never written in a 50000-step run.

How we got this data

  • A normal run saves the planes every 5000 steps which gives only 10 frames per heartbeat (50000-step run). So we ran the case once more (4 nodes, AVX2, monitoring off) with the planes saved every 500 steps, which gives 100 frames.
  • The frames are saved in a binary file .dat (from the dependencies used, it seems to use the XDR binary format) which is converted to plain text using hemeXtract. A python script converts plain text to VTK files. ParaView 6.0.1 then draws these as images. Images are laid out using matplotlib and frames are combined using ffmpeg.
